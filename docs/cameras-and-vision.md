# Камеры и компьютерное зрение

Подсистема живёт в `backend/vision/` и работает в основном бэкенде (порт 8000, на Raspberry Pi — там же).
Она **не зависит** от `TrafficController` и GPIO: результат отдаётся через callbacks, поэтому модуль можно вынести на
отдельный компьютер, оставив светофоры на Raspberry Pi (Task 34.10).

```
CameraSource ──► Detector ──► TrafficAnalyzer ──► TrafficSnapshot
 (кадры)        (объекты)     (трекер, зоны)        │
                                                    ├─► Dashboard (метрики, видео с разметкой)
                                                    ├─► TrafficController.set_data_health()  → FAILSAFE
                                                    └─► SimulationBridge → Smart Intersection (только Simulation Mode)
```

`TrafficAnalyzer` получает только список `Detection` и не знает, откуда они: реальная камера, видеофайл, YOLO или
3D-симуляция (Task 55).

## Источники кадров (`CameraSource`)

| `source` | Что это | Зависимости |
|----------|---------|-------------|
| `simulation` | виртуальная камера-«обскура» над Smart Intersection: перспективная картинка + виртуальные детекции (Task 56) | Pillow |
| `usb` | USB-камера, `uri` = индекс устройства (`"0"`) | OpenCV |
| `file` | видеофайл по кругу — замена камеры в WSL | OpenCV |
| `network` | RTSP / HTTP-поток | OpenCV |
| `image` | одна картинка (тестовый источник) | Pillow |

Камера **не обязательна** для запуска бэкенда и Dashboard. `GET /api/vision/discover` показывает доступные USB-камеры.
Чтобы добавить новый тип камеры, достаточно унаследовать `CameraSource` (`open()`, `read()`, `close()`).

## Детекторы (`Detector`)

| `detector` | Описание |
|------------|----------|
| `virtual` | берёт детекции, приложенные к кадру виртуальным источником (без камеры и без YOLO) |
| `yolo` | локальный YOLO (`ultralytics`), **только CPU**, без CUDA; `pip install -r requirements-yolo.txt` |
| `none` | только картинка без анализа (система остаётся в FAILSAFE) |

Заменяемые параметры: модель (`model_path`), порог уверенности (`confidence`), отслеживаемые классы (`classes`),
размер входа (`imgsz`, для Raspberry Pi 3B+ разумно 320), `device`. Пороги и классы можно менять на лету:
`PATCH /api/vision/cameras/{id}/config`.

Классы проекта: `person`, `car`, `truck`, `bus`, `tram` (COCO `train`), `motorcycle`, `bicycle`, `emergency`.
Собственные классы дообученной модели подключаются через `class_map`
(`ambulance`, `police car`, `fire truck` → `emergency`).

Если пакет `ultralytics` или файл модели отсутствуют, детектор помечается `unavailable`: картинка с камеры продолжает
показываться, система уходит в FAILSAFE, backend не падает.

## Анализ дорожной ситуации

Трекер по центроидам даёт стабильные `track_id`, признак «стоит / едет» и направление. Для каждой зоны считаются:
количество объектов по классам, ожидающие (стоящие), плотность (`count / capacity`), поток (объектов в минуту),
среднее и максимальное время ожидания. Итоговые метрики: автомобили, грузовики, пешеходы, интенсивность
(`vehicles_per_hour`), плотность, направление подъезда, спецтранспорт по направлениям.

**Приоритет пешеходов (Task 13).** Если на переходе ждут не меньше `PEDESTRIAN_PRIORITY_THRESHOLD` человек, зона получает
флаг `ped_priority`; светофоры сокращают конфликтующий зелёный (не раньше `MIN_GREEN`) и дают фазу пешеходам.

## Камера как модель (`camera_model.py`)

Виртуальная камера — не «радар сверху», а камера-обскура (`PinholeCamera`): позиция мачты `x, z`, высота `height_m`,
азимут `yaw_deg` (0 = север, 90 = восток), наклон вниз `pitch_deg` (90 = вертикально вниз), горизонтальный угол обзора
`fov_deg` (вертикальный следует из пропорций кадра) и дальность `range_m`. `yaw/pitch = null` — камера сама
наводится на середину перекрёстка. Пустые `x, z` = камера по умолчанию: над серединой перекрёстка на высоте `2.8 × полуразмер
центра`, обзор 100°, так что видны все подъезды.

`SimulationSource` берёт у Smart Intersection только данные: XML состояния (позиции `x, z, heading` каждого объекта) и
`GET /geometry` (центр, полосы, переходы, столбы светофоров, остров кольца). По ним камера

- рисует картинку с перспективой: дорога с числом полос и разметкой, стоп-линии, переходы, кольцо, светофоры, машины как
  трёхмерные коробки (а не квадраты), пешеходы;
- находит детекции: рамка = проекция коробки объекта, только внутри кадра и дальности, с оценкой видимости; объект,
  закрытый ближайшим, не детектируется; каждая детекция несёт точку касания земли (`foot`);
- строит зоны: подъезд каждой полосы (`north-in`, `north-in-1`, …) и переход проецируются в кадр; в набор попадает только то,
  что камера реально видит (≥ 35 % полигона в кадре, в пределах дальности). Плечо позади камеры не даёт зон.

**Настоящая камера на макете.** Те же поля можно задать любой камере (`usb`, `file`, `network`) в `cameras.yaml`:
`x, z, height_m, yaw_deg, pitch_deg, fov_deg` (обмерьте мачту макета). Зоны полос и переходов проецируются в её кадр
автоматически (`POST /api/vision/sync-layout`), полигоны рисовать не нужно. Анализатор относит объект к зоне по точке
касания земли `(x, y + h/2)` рамки — для перспективной камеры это единственно верное правило.

## Зоны

Зоны задаются полигонами в нормализованных координатах кадра (`config/cameras.yaml`):

- `kind: lane` — считаются транспортные средства (подъезд к стоп-линии), `direction` = плечо перекрёстка;
- `kind: pedestrian` — считаются люди (переход и место ожидания).

Симуляционная камера строит зоны автоматически: по одной на полосу (`north-in`, `north-in-1`, … до `-in-3`) и на переход
(`PC-N` … `PC-W`), только те, что видны камере. Спрос по плечу для светофоров = сумма его полос.
Без зон камера использует одну зону на весь кадр.

## Здоровье и FAILSAFE (Task 7, 24)

Пайплайн сообщает `healthy = False` и причину, когда:

- камера отключена (в том числе кнопкой «Отключить камеру»);
- нет кадров дольше `timeout_s` (по умолчанию 2 с; кратковременный пропуск терпится);
- камеру не удаётся открыть / чтение падает (повторные попытки каждые `reconnect_s`, ошибка логируется один раз);
- детектор недоступен или упал (`DETECTOR_FAILURES_BEFORE_UNHEALTHY` = 3 подряд, недоступность — сразу).

Реакция (`TrafficController.set_data_health`):

- AUTO → FAILSAFE (фиксированные тайминги), причина показывается на Dashboard;
- MANUAL не трогается; при выходе из MANUAL в AUTO без камеры система переходит в FAILSAFE;
- FAILSAFE, выбранный пользователем, не отменяется восстановлением камеры;
- камера вернулась → автоматический возврат в AUTO.

Frontend продолжает работать: вместо картинки показывается плейсхолдер `NO SIGNAL` / `CAMERA DISCONNECTED`.

## Simulation Mode: цепочка с обратной связью

```
Smart Intersection (8001) ──XML /sensor/camera-feed──► виртуальная камера ──► детекции ──► анализ (8000)
        ▲                                                                                      │
        └───────────────────────────── POST /perception (спрос по плечам, флаги) ◄────────────┘
```

- SI управляет сигналами по данным камеры (`perception`); без пакетов дольше 3 с (масштабируется скоростью симуляции)
  или при `camera_ok=false` он переходит на фиксированные тайминги (20 с зелёного).
- Пока основной бэкенд не подключён, SI использует собственные точные данные (это не сбой).
- Сценарий «Camera/Detection Failure» отключает виртуальную камеру (`POST /simulation/camera-failure`,
  `/sensor/camera-feed` отвечает 503); тот же сбой можно включить кнопкой в 3D-интерфейсе.

## API

| Метод | URL | Описание |
|-------|-----|----------|
| GET | `/api/vision/cameras` | состояние камер, детектора, анализ |
| GET | `/api/vision/cameras/{id}` | одна камера (зоны, детекции) |
| GET | `/api/vision/cameras/{id}/stream?overlay=&zones=` | MJPEG-поток с разметкой (`<img src=...>`) |
| GET | `/api/vision/cameras/{id}/snapshot.jpg` | один кадр |
| GET | `/api/vision/cameras/{id}/detections` | детекции и анализ |
| POST | `/api/vision/cameras/{id}/connect` / `disconnect` | подключить / отключить камеру |
| PATCH | `/api/vision/cameras/{id}/config` | порог уверенности, классы |
| GET | `/api/vision/analysis` | сводный анализ |
| GET | `/api/vision/discover` | доступные USB-камеры |

WebSocket `/ws` содержит блок `vision` (состояния камер и анализ без тяжёлых полей).
Метрики системы включают `camera_status`, `camera_fps`, `yolo_status`.

## Настройка

Файл `config/cameras.yaml` (примеры USB / файла / сети — в комментариях) и переменные окружения:
`VISION_ENABLED`, `VISION_CONFIG_PATH`, `SI_BASE_URL`, `VISION_PUSH_TO_SIMULATION`, `PEDESTRIAN_PRIORITY_THRESHOLD`.
Ошибочный `cameras.yaml` не останавливает backend: ошибка логируется, камеры не запускаются.

## Переносимость (WSL Debian 12 ↔ Raspberry Pi 3B+)

- Общий код один; различаются только источник кадров и GPIO. В WSL камеру заменяет `file` или `simulation`.
- OpenCV и Pillow ставятся из wheel-пакетов (на 32-битной Raspberry Pi OS — из piwheels). CUDA не нужна.
- YOLO тяжёлый: на Raspberry Pi 3B+ используйте `yolov8n`, `imgsz: 320`, `fps: 2–3` либо запустите зрение на другом
  компьютере, а на Raspberry Pi оставьте контроллер и GPIO.
- Нужно физически проверить на Raspberry Pi: реальную USB-камеру, скорость YOLO, пропускную способность USB.

## Тесты

```bash
pytest tests/test_vision_*.py -v            # источники, детекторы, анализ, пайплайн, API
pytest tests/test_e2e_vision.py -v          # два реальных процесса: SI + backend (около 40 с)
pytest smart_intersection/tests -v          # симуляция, включая канал восприятия и сбой камеры
```

Тесты не требуют ни камеры, ни Raspberry Pi, ни YOLO: модель подменяется, USB-камера проверяется на отсутствие устройства.

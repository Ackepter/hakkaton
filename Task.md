# Проект: веб-система управления «умным перекрёстком»

*Перед прочтением этого файла зайди в task_files и прочитай все файлы оттуда.

## 1. Цель проекта

Разработать кроссплатформенное веб-приложение для моделирования, мониторинга и управления умным дорожным перекрёстком.

Система должна:

- позволять визуально создавать конфигурацию перекрёстка, создай удобный конструктор, чтобы можно было выставлять полосы, светофоры, камеры, откуда будут ехать машины, пешеходы, их кол-во и т.д. Учти возможность добавлять трамваи, полосы для автобусов и прочие возможности, придумай какие могут быть ещё.
  
- управлять светофорами;
  
- получать изображение с камер;
  
- распознавать автомобили, грузовики, пешеходов и другие объекты;
  
- рассчитывать статистику дорожного движения;
  
- автоматически выбирать режим работы светофоров на основе дорожной ситуации;
  
- иметь аварийный режим при потере данных с камер;
  
- поддерживать ручное управление;
  
- проект должен иметь веб интерфейс, который будет отображаться на пк, весь бэк и работа с реальными камерами, светофором и т.д. висит на распбери.

- Система должна на основе собранной статистики определять, какие метрики изменить, чтобы ситуация была оптимальной (оптимальная эта та, где время простоя машин, в первую очередь, и пешеходов, во вторую, минимальна). То бишь пользователь задаёт конфигурацию и наглядно видит, что в ней не так.

Главный приоритет проекта — **простота запуска, надёжность и возможность демонстрации на физическом макете перекрёстка**, будем использовать распбери 3b+. Пока твоя задача создать симуляцию и этот веб конструктор, распбери подключим попозже

# 2. Технологические требования

Выбирай технологии с учётом следующих требований:

1. Проект должен легко запускаться на Windows и Linux.
   
2. Проект должен работать на Raspberry Pi.
   
3. Не использовать технологии, которые требуют сложной инфраструктуры для запуска.
   
4. Архитектура должна позволять отдельно запускать backend и frontend.
   
5. Все настройки должны храниться в конфигурации, а не быть жёстко зашиты в код.
   
6. Камера должна подключаться через стандартный интерфейс, например USB.
   
7. Необходимо предусмотреть возможность дальнейшего подключения других типов камер.
   
8. AI/ML-компоненты должны работать локально, без обязательного подключения к облачным API.
   

Предпочтительный вариант:

- Backend: Python.
  
- Web framework: FastAPI или Django.
  
- Frontend: React либо другой простой современный web frontend.
  
- Computer Vision: OpenCV.
  
- Object Detection: YOLO.
  
- Хранение конфигурации: JSON/YAML на первом этапе либо PostgreSQL/SQLite, если это действительно необходимо.
  
- Для физического управления светодиодами Raspberry Pi использовать отдельный модуль/слой аппаратного управления.
  

Не усложняй архитектуру без необходимости.

# 7. Аварийный режим

Критически важная функция.

Если система перестала получать данные с камеры или потеряла возможность анализировать дорожную ситуацию, система должна автоматически переходить в безопасный заранее заданный режим.

Например:

```text
NORMAL MODE
     ↓
Camera unavailable
     ↓
FAILSAFE MODE
     ↓
Fixed traffic-light timing
```

В аварийном режиме светофоры работают по заранее заданным таймингам.

Пользователь должен видеть в интерфейсе:

- NORMAL;
  
- FAILSAFE;
  
- MANUAL.
  

При переходе в аварийный режим желательно отображать причину. Так же система должна активно сигнализировать о сбое, например, "вызвав" специалистов.

# 9. Ручное управление

Необходимо предусмотреть MANUAL MODE.

Пользователь должен иметь возможность вручную:

- включить/выключить режим;
  
- изменить состояние светофора;
  
- переключить фазу;
  
- при необходимости принудительно включить красный/жёлтый/зелёный.
  

Ручное управление должно иметь более высокий приоритет, чем автоматическая логика.

После отключения ручного режима система должна корректно вернуться в AUTO либо FAILSAFE.

# 12. Анализ дорожной ситуации

На основе результатов object detection рассчитывать состояние дорожного потока.

- количество автомобилей;

- направление движения, если это возможно;
  
- интенсивность потока;
  
- приблизительную плотность транспорта.
  

Камера должна быть привязана к определённым зонам перекрёстка.

Например:

```text

 ├── Zone A

```

# 13. Приоритет пешеходов

Необходимо реализовать специальную логику:

Если на пешеходном переходе скопилось большое количество людей, система должна учитывать это при выборе следующей фазы.

Например:

```text
Few pedestrians
→ обычный режим

Many pedestrians
→ повышенный приоритет пешеходной фазы
```

Порог количества пешеходов должен быть настраиваемым.

# 14. Автоматическое управление светофорами

Система должна иметь AUTO MODE.

В автоматическом режиме решение о переключении фаз принимается на основании текущей дорожной ситуации.

Факторы могут включать:

- количество автомобилей;
  
- плотность потока;
  
- количество ожидающих автомобилей;
  
- количество пешеходов;
  
- длительность ожидания;
  
- приоритет конкретного направления;
  
- состояние других полос.
  

Алгоритм управления должен быть отдельным модулем.

Например:

```text
Camera
   ↓
Object Detection
   ↓
Traffic Analysis
   ↓
Traffic Controller
   ↓
Traffic Lights
```

Не смешивать распознавание объектов и управление светофорами в одном классе.

# 20. Архитектура физического управления

Не привязывать бизнес-логику напрямую к GPIO.

Использовать абстракцию:

```text
TrafficController
       ↓
TrafficLightHardware
       ↓
GPIO / Raspberry Pi
```

На обычном компьютере должен существовать MockHardware.

Например:

```text
Windows
   ↓
Mock GPIO
   ↓
виртуальный светофор
```

А на Raspberry Pi:

```text
Raspberry Pi
   ↓
Real GPIO
   ↓
физический светофор
```

Это необходимо для разработки без Raspberry Pi.

# 24. Обработка ошибок

```text

→ vision module unavailable
→ traffic controller switches to FAILSAFE
→ frontend continues working
```

Аналогично:

```text
YOLO failed
→ camera image still displayed
→ system enters FAILSAFE
```

Все ошибки должны логироваться.

# 34. Совместимость WSL Debian 12 и Raspberry Pi 3B+

Это обязательное архитектурное требование проекта.

Проект будет сначала разрабатываться и тестироваться на компьютере в WSL2, а затем переноситься на Raspberry Pi 3B+.

## 34.1. Целевые операционные системы

Основная целевая ОС Raspberry Pi:

- Raspberry Pi OS Legacy 64-bit;
- Debian 12 Bookworm;
- архитектура ARM64 / aarch64.

Основная среда разработки:

- WSL2;
- Debian 12 Bookworm;
- архитектура компьютера может быть x86_64.

Учитывать, что WSL на обычном ПК и Raspberry Pi имеют разные архитектуры CPU.

Совпадение версии Debian НЕ означает, что собранные бинарные файлы или Python wheels для x86_64 можно напрямую перенести на ARM64.

## 34.2. Основной принцип переносимости

Один проект должен максимально одинаково работать в двух средах:

```text
WSL2 Debian 12 x86_64
        ↓
разработка и тестирование
        ↓
Raspberry Pi OS Legacy 64-bit
Debian 12 ARM64
        ↓
физический макет
```

Не создавать отдельную кодовую базу для Raspberry Pi.

Платформозависимый код должен быть изолирован в отдельных модулях.

## 34.3. Требования к зависимостям

При выборе каждой новой библиотеки агент должен учитывать:

1. работает ли она в Debian 12 x86_64;
2. существует ли поддержка Debian 12 ARM64/aarch64;
3. доступна ли она на Raspberry Pi 3B+;
4. не требует ли она NVIDIA CUDA;
5. не требует ли она x86_64-only бинарных компонентов;
6. действительно ли она необходима проекту.

Приоритет выбора зависимостей:

1. стандартная библиотека Python;
2. системные пакеты Debian;
3. Python-пакеты с поддержкой ARM64;
4. более тяжелые или платформозависимые решения — только если без них нельзя обойтись.

Не добавлять зависимость только ради удобства разработки, если она создаёт проблемы с переносимостью.

## 34.4. Python

Использовать Python 3 с виртуальным окружением.

Все Python-зависимости должны быть явно зафиксированы в `requirements.txt` либо в другом понятном файле управления зависимостями.

В README должны быть приведены команды установки и запуска для:

- WSL Debian 12;
- Raspberry Pi OS Bookworm.

Не полагаться на глобально установленные Python-пакеты.

## 34.5. Hardware Abstraction Layer

Код управления физическими светофорами НЕ должен напрямую находиться внутри бизнес-логики.

Использовать аппаратную абстракцию.

Рекомендуемая архитектура:

```text
TrafficController
        ↓
TrafficLightHardware
        ↓
 ┌───────────────┬────────────────────┐
 ↓               ↓                    ↓
MockGPIO     RaspberryPiGPIO     FutureHardware
```

`TrafficController` и остальная логика системы не должны знать, используется реальный GPIO или эмуляция.

## 34.6. Mock GPIO

В WSL не должно требоваться наличие Raspberry Pi.

Необходимо реализовать `MockGPIO` / `MockHardware`.

Mock-реализация должна позволять:

- включать и выключать виртуальные сигналы;
- получать текущее состояние каждого GPIO;
- отображать состояние в логах;
- использовать виртуальное состояние в Dashboard;
- тестировать переключение фаз;
- тестировать MANUAL;
- тестировать AUTO;
- тестировать FAILSAFE.

Пример:

```text
Mock GPIO:

TL-01
RED    = ON
YELLOW = OFF
GREEN  = OFF
```

## 34.7. Реальный GPIO

Для Raspberry Pi создать отдельную реализацию аппаратного слоя.

Например:

```text
TrafficLightHardware
        ↓
RaspberryPiGPIO
        ↓
GPIO pins
        ↓
LED traffic light
```

GPIO-пины не должны быть жестко зашиты в бизнес-логику.

Например:

```yaml
traffic_lights:
  TL-01:
    red_pin: 17
    yellow_pin: 27
    green_pin: 22
```

Конкретные GPIO-пины должны задаваться через конфигурацию.

## 34.8. Режимы запуска

- видеофайл или тестовый видеопоток;

Этот режим используется для разработки и тестирования алгоритмов управления светофорами.

### Raspberry Pi

## 34.10. YOLO и Raspberry Pi 3B+

YOLO должен быть отдельным модулем компьютерного зрения.

Не смешивать:

```text

```

с:

```text

```

и:

```text

```

Архитектура должна позволять заменить:

Не делать CUDA обязательной зависимостью.

Учитывать ограниченные вычислительные ресурсы Raspberry Pi 3B+.

Если полное выполнение YOLO на Raspberry Pi 3B+ оказывается слишком тяжелым, архитектура должна позволять в будущем вынести компьютерное зрение на отдельный компьютер, оставив управление светофорами и основной backend на Raspberry Pi.

# 38. Главное архитектурное правило

При любых архитектурных решениях руководствоваться следующим принципом:

> Сначала сделать максимально простой и полностью работающий вариант в WSL Debian 12, который можно протестировать без физического оборудования. Затем заменить только платформозависимые компоненты на реализации Raspberry Pi.

Не делать Raspberry Pi главным ограничением всего проекта.

Не делать WSL отдельной версией проекта.

Цель — одна кодовая база с различающимися реализациями только там, где это действительно необходимо:

```text
                COMMON CODE
                     │
       ┌─────────────┴─────────────┐
       │                           │
   WSL/PC                      Raspberry Pi
       │                           │
   Mock GPIO                   Real GPIO
   Video File                  USB Camera
   Simulation                  Physical Model
```

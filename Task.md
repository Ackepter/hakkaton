# Проект: веб-система управления «умным перекрёстком»

*Перед прочтением этого файла зайди в task_files и прочитай все файлы оттуда.

## 1. Цель проекта

Разработать кроссплатформенное веб-приложение для моделирования, мониторинга и управления умным дорожным перекрёстком.

Система должна:

- позволять визуально создавать конфигурацию перекрёстка, создай удобный конструктор, чтобы можно было выставлять полосы, светофоры, камеры, откуда будут ехать машины, пешеходы, их кол-во и т.д. Учти возможность добавлять трамваи, полосы для автобусов и прочие возможности, придумай какие могут быть ещё.
  
- управлять светофорами;
  
- получать изображение с камер;
  
- распознавать автомобили, грузовики, пешеходов и другие объекты;
  
- рассчитывать статистику дорожного движения;
  
- автоматически выбирать режим работы светофоров на основе дорожной ситуации;
  
- иметь аварийный режим при потере данных с камер;
  
- поддерживать ручное управление;
  
- проект должен иметь веб интерфейс, который будет отображаться на пк, весь бэк и работа с реальными камерами, светофором и т.д. висит на распбери.

- Система должна на основе собранной статистики определять, какие метрики изменить, чтобы ситуация была оптимальной (оптимальная эта та, где время простоя машин, в первую очередь, и пешеходов, во вторую, минимальна). То бишь пользователь задаёт конфигурацию и наглядно видит, что в ней не так.

Главный приоритет проекта — **простота запуска, надёжность и возможность демонстрации на физическом макете перекрёстка**, будем использовать распбери 3b+. Пока твоя задача создать симуляцию и этот веб конструктор, распбери подключим попозже

# 2. Технологические требования

Выбирай технологии с учётом следующих требований:

1. Проект должен легко запускаться на Windows и Linux.
   
2. Проект должен работать на Raspberry Pi.
   
3. Не использовать технологии, которые требуют сложной инфраструктуры для запуска.
   
4. Архитектура должна позволять отдельно запускать backend и frontend.
   
5. Все настройки должны храниться в конфигурации, а не быть жёстко зашиты в код.
   
6. Камера должна подключаться через стандартный интерфейс, например USB.
   
7. Необходимо предусмотреть возможность дальнейшего подключения других типов камер.
   
8. AI/ML-компоненты должны работать локально, без обязательного подключения к облачным API.
   

Предпочтительный вариант:

- Backend: Python.
  
- Web framework: FastAPI или Django.
  
- Frontend: React либо другой простой современный web frontend.
  
- Computer Vision: OpenCV.
  
- Object Detection: YOLO.
  
- Хранение конфигурации: JSON/YAML на первом этапе либо PostgreSQL/SQLite, если это действительно необходимо.
  
- Для физического управления светодиодами Raspberry Pi использовать отдельный модуль/слой аппаратного управления.
  

Не усложняй архитектуру без необходимости.

# 7. Аварийный режим

Критически важная функция.

Если система перестала получать данные с камеры или потеряла возможность анализировать дорожную ситуацию, система должна автоматически переходить в безопасный заранее заданный режим.

Например:

```text
NORMAL MODE
     ↓
Camera unavailable
     ↓
FAILSAFE MODE
     ↓
Fixed traffic-light timing
```

В аварийном режиме светофоры работают по заранее заданным таймингам.

Пользователь должен видеть в интерфейсе:

- NORMAL;
  
- FAILSAFE;
  
- MANUAL.
  

При переходе в аварийный режим желательно отображать причину. Так же система должна активно сигнализировать о сбое, например, "вызвав" специалистов.

# 9. Ручное управление

Необходимо предусмотреть MANUAL MODE.

Пользователь должен иметь возможность вручную:

- включить/выключить режим;
  
- изменить состояние светофора;
  
- переключить фазу;
  
- при необходимости принудительно включить красный/жёлтый/зелёный.
  

Ручное управление должно иметь более высокий приоритет, чем автоматическая логика.

После отключения ручного режима система должна корректно вернуться в AUTO либо FAILSAFE.

- интенсивность потока;
  
- приблизительную плотность транспорта.
  

Камера должна быть привязана к определённым зонам перекрёстка.

Например:

# 13. Приоритет пешеходов

Необходимо реализовать специальную логику:

Если на пешеходном переходе скопилось большое количество людей, система должна учитывать это при выборе следующей фазы.

Например:

```text
Few pedestrians
→ обычный режим

Many pedestrians
→ повышенный приоритет пешеходной фазы
```

Порог количества пешеходов должен быть настраиваемым.

# 14. Автоматическое управление светофорами

Система должна иметь AUTO MODE.

В автоматическом режиме решение о переключении фаз принимается на основании текущей дорожной ситуации.

Факторы могут включать:

- количество автомобилей;
  
- плотность потока;
  
- количество ожидающих автомобилей;
  
- количество пешеходов;
  
- длительность ожидания;
  
- приоритет конкретного направления;
  
- состояние других полос.
  

Алгоритм управления должен быть отдельным модулем.

Например:

```text
Camera
   ↓
Object Detection
   ↓
Traffic Analysis
   ↓
Traffic Controller
   ↓
Traffic Lights
```

Не смешивать распознавание объектов и управление светофорами в одном классе.

# 20. Архитектура физического управления

Не привязывать бизнес-логику напрямую к GPIO.

Использовать абстракцию:

```text
TrafficController
       ↓
TrafficLightHardware
       ↓
GPIO / Raspberry Pi
```

На обычном компьютере должен существовать MockHardware.

Например:

```text
Windows
   ↓
Mock GPIO
   ↓
виртуальный светофор
```

А на Raspberry Pi:

```text
Raspberry Pi
   ↓
Real GPIO
   ↓
физический светофор
```

Это необходимо для разработки без Raspberry Pi.


```text

→ camera image still displayed
→ system enters FAILSAFE
```

# 34. Совместимость WSL Debian 12 и Raspberry Pi 3B+

Это обязательное архитектурное требование проекта.

Проект будет сначала разрабатываться и тестироваться на компьютере в WSL2, а затем переноситься на Raspberry Pi 3B+.

## 34.1. Целевые операционные системы

Основная целевая ОС Raspberry Pi:

- Raspberry Pi OS Legacy 64-bit;
- Debian 12 Bookworm;
- архитектура ARM64 / aarch64.

Основная среда разработки:

- WSL2;
- Debian 12 Bookworm;
- архитектура компьютера может быть x86_64.

Учитывать, что WSL на обычном ПК и Raspberry Pi имеют разные архитектуры CPU.

Совпадение версии Debian НЕ означает, что собранные бинарные файлы или Python wheels для x86_64 можно напрямую перенести на ARM64.

## 34.2. Основной принцип переносимости

Один проект должен максимально одинаково работать в двух средах:

```text
WSL2 Debian 12 x86_64
        ↓
разработка и тестирование
        ↓
Raspberry Pi OS Legacy 64-bit
Debian 12 ARM64
        ↓
физический макет
```

Не создавать отдельную кодовую базу для Raspberry Pi.

Платформозависимый код должен быть изолирован в отдельных модулях.

## 34.3. Требования к зависимостям

При выборе каждой новой библиотеки агент должен учитывать:

1. работает ли она в Debian 12 x86_64;
2. существует ли поддержка Debian 12 ARM64/aarch64;
3. доступна ли она на Raspberry Pi 3B+;
4. не требует ли она NVIDIA CUDA;
5. не требует ли она x86_64-only бинарных компонентов;
6. действительно ли она необходима проекту.

Приоритет выбора зависимостей:

1. стандартная библиотека Python;
2. системные пакеты Debian;
3. Python-пакеты с поддержкой ARM64;
4. более тяжелые или платформозависимые решения — только если без них нельзя обойтись.

Не добавлять зависимость только ради удобства разработки, если она создаёт проблемы с переносимостью.

## 34.4. Python

Использовать Python 3 с виртуальным окружением.

Все Python-зависимости должны быть явно зафиксированы в `requirements.txt` либо в другом понятном файле управления зависимостями.

В README должны быть приведены команды установки и запуска для:

- WSL Debian 12;
- Raspberry Pi OS Bookworm.

Не полагаться на глобально установленные Python-пакеты.

## 34.5. Hardware Abstraction Layer

Код управления физическими светофорами НЕ должен напрямую находиться внутри бизнес-логики.

Использовать аппаратную абстракцию.

Рекомендуемая архитектура:

```text
TrafficController
        ↓
TrafficLightHardware
        ↓
 ┌───────────────┬────────────────────┐
 ↓               ↓                    ↓
MockGPIO     RaspberryPiGPIO     FutureHardware
```

`TrafficController` и остальная логика системы не должны знать, используется реальный GPIO или эмуляция.

## 34.6. Mock GPIO

В WSL не должно требоваться наличие Raspberry Pi.

Необходимо реализовать `MockGPIO` / `MockHardware`.

Mock-реализация должна позволять:

- включать и выключать виртуальные сигналы;
- получать текущее состояние каждого GPIO;
- отображать состояние в логах;
- использовать виртуальное состояние в Dashboard;
- тестировать переключение фаз;
- тестировать MANUAL;
- тестировать AUTO;
- тестировать FAILSAFE.

Пример:

```text
Mock GPIO:

TL-01
RED    = ON
YELLOW = OFF
GREEN  = OFF
```

## 34.7. Реальный GPIO

Для Raspberry Pi создать отдельную реализацию аппаратного слоя.

Например:

```text
TrafficLightHardware
        ↓
RaspberryPiGPIO
        ↓
GPIO pins
        ↓
LED traffic light
```

GPIO-пины не должны быть жестко зашиты в бизнес-логику.

Например:

```yaml
traffic_lights:
  TL-01:
    red_pin: 17
    yellow_pin: 27
    green_pin: 22
```

Конкретные GPIO-пины должны задаваться через конфигурацию.

## 34.8. Режимы запуска

## 34.10. YOLO и Raspberry Pi 3B+

YOLO должен быть отдельным модулем компьютерного зрения.

Не смешивать:

```text

```

с:

```text

```

и:

```text

```

Архитектура должна позволять заменить:

Не делать CUDA обязательной зависимостью.

Учитывать ограниченные вычислительные ресурсы Raspberry Pi 3B+.

Если полное выполнение YOLO на Raspberry Pi 3B+ оказывается слишком тяжелым, архитектура должна позволять в будущем вынести компьютерное зрение на отдельный компьютер, оставив управление светофорами и основной backend на Raspberry Pi.

# 38. Главное архитектурное правило

При любых архитектурных решениях руководствоваться следующим принципом:

> Сначала сделать максимально простой и полностью работающий вариант в WSL Debian 12, который можно протестировать без физического оборудования. Затем заменить только платформозависимые компоненты на реализации Raspberry Pi.

Не делать Raspberry Pi главным ограничением всего проекта.

Не делать WSL отдельной версией проекта.

Цель — одна кодовая база с различающимися реализациями только там, где это действительно необходимо:

```text
                COMMON CODE
                     │
       ┌─────────────┴─────────────┐
       │                           │
   WSL/PC                      Raspberry Pi
       │                           │
   Mock GPIO                   Real GPIO
   Video File                  USB Camera
   Simulation                  Physical Model
```

# 39. Smart Intersection — отдельный микросервис 3D-симуляции

## 39.1. Приоритет этого раздела

Данный раздел является уточнением и расширением существующих требований проекта.

Если требования этого раздела противоречат более ранним требованиям, относящимся непосредственно к:

- Smart Intersection;

- визуализации перекрёстка;

приоритет имеют требования данного раздела.

# 40. Основная идея Smart Intersection

`Smart Intersection` должен быть реализован как **самостоятельный сервис**, отвечающий за моделирование и симуляцию дорожного перекрёстка.

Это не должна быть просто 2D-схема или набор HTML-элементов.

Необходимо создать полноценную интерактивную **3D-симуляцию дорожного движения**, визуально напоминающую упрощённый градостроительный симулятор.

По концепции она должна быть ближе к:

- Cities: Skylines;
- транспортным симуляторам;
- упрощённым city-builder играм;

но масштаб и сложность должны соответствовать учебному/демонстрационному проекту.

Главная цель — пользователь должен видеть не абстрактные цифры, а реальный виртуальный перекрёсток, на котором:

- существуют дороги;
- существуют полосы;
- ездят автомобили;
- ездят грузовики;
- могут ездить автобусы;
- могут присутствовать трамваи;
- ходят пешеходы;
- работают светофоры;
- автомобили останавливаются на красный;
- автомобили продолжают движение на зелёный;
- пешеходы используют переходы;
- изменяются транспортные потоки;
- возникают очереди;
- меняются статистические показатели;
- алгоритм Smart Intersection может менять работу светофоров.

------

# 41. Граница ответственности Smart Intersection

Smart Intersection является отдельным микросервисом.

Он должен иметь собственный backend и собственную логику симуляции.

Архитектурно:

```text
                         MAIN PROJECT
                              │
                    ┌─────────┴─────────┐
                    │                   │
                Dashboard          Other modules
                    │
                    │ API
                    │
                    ▼
          ┌──────────────────────┐
          │   SMART INTERSECTION │
          │      SERVICE         │
          │                      │
          │  3D Simulation       │
          │  Traffic Engine      │
          │  Pedestrian Engine   │
          │  Traffic Lights      │
          │  Metrics             │
          │  Scenario Engine     │
          │  XML Export          │
          └──────────────────────┘
```

Smart Intersection не должен напрямую обращаться к внутренним классам Dashboard.

Dashboard не должен импортировать код Smart Intersection.

Связь между ними должна происходить только через публичный API.

------

# 42. API Smart Intersection

Smart Intersection должен предоставлять отдельный HTTP API.

Предпочтительно использовать REST API.

При необходимости для real-time обновлений можно использовать WebSocket.

Пример:

```text
Main application
       │
       │ HTTP API
       ▼
Smart Intersection
       │
       ├── Simulation
       ├── Traffic Engine
       ├── Pedestrian Engine
       ├── Traffic Lights
       └── Metrics
```

Минимально предусмотреть API для:

```text
POST   /simulation/start
POST   /simulation/stop
POST   /simulation/pause
POST   /simulation/reset

GET    /simulation/state
GET    /simulation/config

POST   /simulation/config

GET    /traffic-lights
POST   /traffic-lights/{id}/state

GET    /metrics
GET    /statistics

POST   /scenario/start
POST   /scenario/stop

GET    /health
```

Конкретные endpoints можно изменить, если агент предложит более технически обоснованный вариант.

API должен быть документирован.

Для FastAPI желательно автоматически использовать OpenAPI/Swagger.

------

# 43. XML как основной формат обмена данными

Критически важно:

**Smart Intersection должен формировать XML-файл/документ с результатами симуляции.**

Остальная система не должна получать внутренние Python-объекты Smart Intersection.

Поток данных:

```text
Smart Intersection
       │
       │
       ▼
    XML data
       │
       ▼
Main application
       │
       ▼
XML parser
       │
       ▼
Dashboard
       │
       ▼
Statistics / graphs / analytics
```

XML должен быть стандартизированным и иметь стабильную схему.

Необходимо создать XML Schema Definition (`.xsd`) либо другой формальный способ описания структуры XML.

# 44. Формат XML

Предусмотреть структуру примерно следующего вида:

```xml
<intersectionSimulation
    version="1.0"
    timestamp="2026-09-26T20:00:00Z">

    <intersection id="intersection-01">

        <simulation>
            <status>running</status>
            <simulationTime>125.4</simulationTime>
            <timeScale>1.0</timeScale>
        </simulation>

        <trafficLights>
            <trafficLight id="TL-01">
                <state>GREEN</state>
                <phase>north_south</phase>
                <remainingTime>12.5</remainingTime>
            </trafficLight>
        </trafficLights>

        <vehicles>
            <vehicle
                id="car-001"
                type="car"
                lane="north-01"
                speed="8.4"
                waiting="false"/>

            <vehicle
                id="truck-002"
                type="truck"
                lane="east-01"
                speed="0"
                waiting="true"/>
        </vehicles>

        <pedestrians>
            <pedestrian
                id="ped-001"
                crossing="crossing-01"
                state="waiting"/>
        </pedestrians>

        <metrics>
            <vehicleCount>17</vehicleCount>
            <pedestrianCount>8</pedestrianCount>
            <averageVehicleWaitingTime>14.3</averageVehicleWaitingTime>
            <averagePedestrianWaitingTime>7.8</averagePedestrianWaitingTime>
            <throughput>42</throughput>
        </metrics>

    </intersection>
</intersectionSimulation>
```

Это только пример.

Агент должен разработать окончательную XML-схему таким образом, чтобы она позволяла передавать всю информацию, необходимую Dashboard.

### Транспорт

Для каждого транспортного объекта при необходимости:

- ID;
- тип;
- положение;
- направление;
- полоса;
- скорость;
- состояние;
- время ожидания.

### Пешеходы

- ID;
- положение;
- переход;
- направление;
- состояние;
- время ожидания.

### Метрики

- количество автомобилей;
- количество грузовиков;
- количество автобусов;
- количество трамваев;
- количество пешеходов;
- количество ожидающих автомобилей;
- количество ожидающих пешеходов;
- среднее время ожидания;

# 47. 3D Simulation Engine

Smart Intersection должен содержать полноценный 3D simulation engine.

Необходимо создать визуальную сцену минимум с:

### Дорожной инфраструктурой

- асфальтовая дорога;
- перекрёсток;
- дорожные полосы;
- разметка;
- стоп-линии;
- тротуары;
- пешеходные переходы;
- бордюры;
- светофоры;
- дорожные знаки.

Желательно добавить:

- фонари;

- здания;
- парковочные зоны;
- остановки общественного транспорта;
- ограждения;

Окружение не должно быть чрезмерно сложным.

Главное — чтобы пользователь визуально воспринимал сцену как настоящий городской перекрёсток.

# 48. Автомобили

В симуляции должны присутствовать реальные 3D-модели транспортных объектов.

Минимально:

```text
Car
Truck
Bus
Tram
```

При этом архитектура должна позволять добавить:

```text
Ambulance
Police
Fire truck
Taxi
Motorcycle
Bicycle
```

без переписывания simulation engine.

Каждый автомобиль должен иметь:

- ID;
- тип;
- положение;
- направление;
- скорость;
- ускорение/торможение;
- текущую полосу;
- целевую полосу;
- состояние;
- маршрут;
- время ожидания.

------

# 49. Поведение автомобилей

Автомобили не должны просто перемещаться по заранее заданным координатам.

Они должны иметь базовую модель поведения.

Минимально реализовать:

```text
FOLLOW_ROUTE
       ↓
APPROACH_INTERSECTION
       ↓
CHECK_TRAFFIC_LIGHT
       ↓
STOP / MOVE
       ↓
PASS_INTERSECTION
       ↓
CONTINUE_ROUTE
```

Автомобиль должен:

- двигаться по своей полосе;
- соблюдать направление;
- останавливаться перед красным;
- останавливаться за другим автомобилем;
- начинать движение после зелёного;
- тормозить;
- ускоряться;
- проезжать перекрёсток;
- не проезжать через другие автомобили;
- учитывать минимальную дистанцию;
- формировать очередь.

Не требуется реализовывать физически точную модель автомобиля.

Достаточно правдоподобной игровой модели движения.

------

# 50. Пешеходы

Необходимо реализовать полноценные пешеходные объекты.

Пешеход должен:

- появляться на тротуаре;
- идти к пешеходному переходу;
- ждать разрешающего сигнала;
- переходить дорогу;
- доходить до противоположной стороны;
- исчезать либо продолжать движение.

Минимальная модель:

```text
SPAWN
 ↓
WAIT_FOR_CROSSING
 ↓
WAIT_FOR_GREEN
 ↓
CROSS
 ↓
FINISH
```

При красном сигнале для пешехода он должен ждать.

При разрешающем сигнале — переходить.

------

# 51. Пешеходные переходы

Переход должен быть отдельным объектом симуляции.

Он должен иметь:

- ID;
- положение;
- направление;
- связанные полосы;
- светофор;
- количество ожидающих пешеходов;
- текущих переходящих пешеходов.

Переходы должны быть видимы в 3D-сцене.

------

# 52. Генератор трафика

Необходимо создать Traffic Generator.

Он должен позволять задавать:

```text
Vehicle spawn rate
Pedestrian spawn rate
Vehicle type probability
Direction probability
Traffic intensity
```

Например:

```yaml
traffic:
  car_probability: 0.75
  truck_probability: 0.10
  bus_probability: 0.10
  tram_probability: 0.05

  spawn_rate: 12
  pedestrian_rate: 5
```

Должна существовать возможность менять интенсивность во время симуляции.

# 53. Сценарии дорожного движения

Создать систему сценариев.

Минимально:

### Scenario 1 — Empty

Почти нет транспорта.

### Scenario 2 — Normal

Обычный городской поток.

### Scenario 3 — Heavy Traffic

Большой поток автомобилей.

### Scenario 4 — Pedestrian Rush

Большое количество пешеходов.

### Scenario 5 — Unbalanced Traffic

Большой поток только с одного направления.

### Scenario 6 — Emergency Vehicle

Появляется машина скорой помощи/полиции.

### Scenario 7 — Traffic Jam

Возникает большая очередь.

### Scenario 8 — Camera/Detection Failure

Система симулирует потерю данных.

# 54. Взаимодействие с Traffic Controller

3D-симуляция не должна содержать отдельную копию алгоритма управления светофорами.

Она должна использовать тот же `Traffic Controller`, который используется остальной системой.

Правильная архитектура:

```text
                 Traffic Controller
                         │
              ┌──────────┴──────────┐
              │                     │
         Real Hardware          Simulation
              │                     │
          GPIO LEDs            3D Lights
```

Таким образом, если Traffic Controller переключил:

```text
TL-01 = GREEN
TL-02 = RED
```

то это должно одновременно отражаться:

- в Simulation;
- в XML;
- в Dashboard;
- в Mock GPIO;
- в будущем — на физическом GPIO.

------

# 55. Simulation как источник данных

3D Simulation должна выступать в роли виртуального источника дорожной информации.

Вместо:

```text
Camera
 ↓
YOLO
 ↓
Traffic Analysis
```

в Simulation Mode:

```text
3D Simulation
 ↓
Virtual Object Detection
 ↓
Traffic Analysis
 ↓
Traffic Controller
```

При этом интерфейсы должны оставаться одинаковыми.

То есть Traffic Analysis не должен знать, поступили данные:

- от реальной камеры;
- от видеофайла;
- от YOLO;
- от 3D Simulation.

------

# 56. Связь Simulation и YOLO

Не требуется заставлять YOLO анализировать рендер самой 3D-сцены.

Для Simulation Mode необходимо создать виртуальный источник detection data.

Например:

```text
Virtual Car
 ↓
Virtual Detection
 ↓
{
    type: "car",
    x: 10.2,
    y: 0,
    lane: "north-01"
}
```

Это позволит тестировать всю систему без камеры и без YOLO.

# 62. 3D Engine — требования к технологии

Выбрать технологию, которая позволяет относительно просто реализовать web-based 3D.

Предпочтительно рассмотреть:

- Three.js;
- Babylon.js;

- другой WebGL/WebGPU-совместимый вариант.

3. производительности;

------

# 63. Разделение Simulation Engine и Renderer

Обязательно разделить:

```text
Simulation Engine
```

и

```text
3D Renderer
```

Например:

```text
Simulation Engine
      │
      │ state
      ▼
3D Renderer
```

Simulation Engine отвечает за:

- движение;
- правила;
- светофоры;
- маршруты;
- генерацию;
- метрики.

Renderer отвечает только за:

- отображение;
- модели;
- освещение;
- камеру;
- визуальные эффекты.

Это позволит запускать simulation tests без браузера.

------

# 64. Детерминированный режим тестирования

Simulation Engine должен поддерживать фиксированный seed.

Например:

```text
seed = 42
```

При одинаковых:

- seed;
- конфигурации;
- длительности;
- начальном состоянии;

результат симуляции должен быть воспроизводимым либо иметь допустимую погрешность.

Это необходимо для автоматических тестов.

# 65. Автоматические тесты Smart Intersection

Не ограничиваться unit-тестами отдельных функций.

Создать несколько уровней тестирования.

## 65.1. Unit tests

Проверить:

- движение автомобиля;
- остановку на красный;
- движение на зелёный;
- торможение;
- дистанцию между автомобилями;
- движение пешехода;
- ожидание пешехода;
- переключение фаз;
- генератор транспорта;
- расчёт метрик;
- XML serialization;
- XML parsing.

# 66. Simulation tests

Создать полноценные сценарии.

### Test 1 — Empty Intersection

Запустить:

```text
seed = 42
traffic = 0
pedestrians = 0
duration = 60 sec
```

Проверить:

- simulation не падает;
- автомобилей нет;
- пешеходов нет;
- светофоры продолжают работать;
- XML создаётся;
- Dashboard может его распарсить.

------

### Test 2 — Basic Traffic

Создать:

```text
10 cars/min
```

Проверить:

- автомобили появляются;
- движутся по маршрутам;
- останавливаются на красный;
- проезжают на зелёный;
- количество автомобилей увеличивается в статистике.

------

### Test 3 — Red Light

Создать автомобиль перед красным.

Проверить:

```text
speed → 0
```

и:

```text
vehicle does not cross stop line
```

------

### Test 4 — Green Light

После переключения:

```text
RED → GREEN
```

проверить:

```text
vehicle starts moving
```

------

### Test 5 — Pedestrian Crossing

Создать пешехода.

Проверить:

```text
WAITING
 ↓
GREEN
 ↓
CROSSING
 ↓
FINISHED
```

------

### Test 6 — Heavy Traffic

Создать интенсивный поток.

Проверить:

- образуется очередь;
- длина очереди рассчитывается;
- average waiting time увеличивается;
- throughput рассчитывается;
- XML содержит правильную статистику.

------

### Test 7 — Pedestrian Priority

Создать большое количество пешеходов.

Проверить:

```text
pedestrian count > threshold
```

приводит к учёту повышенного приоритета пешеходной фазы.

Не проверять конкретный алгоритм как единственно правильный — проверять, что механизм приоритета действительно влияет на decision logic согласно конфигурации.

------

### Test 8 — Unbalanced Traffic

Создать:

```text
North: 30 cars/min
South: 2 cars/min
East: 2 cars/min
West: 2 cars/min
```

Проверить:

- система корректно рассчитывает дисбаланс;
- метрики по направлениям различаются;
- Traffic Controller получает актуальные данные.

------

### Test 9 — Traffic Jam

Создать поток, превышающий пропускную способность перекрёстка.

Проверить:

- очередь увеличивается;
- average waiting time увеличивается;
- queue length рассчитывается;
- система не зависает;
- simulation продолжает работать.

------

### Test 10 — XML Contract

Запустить симуляцию.

Получить XML.

Проверить:

```text
XML valid
XML conforms to XSD
all required fields exist
Dashboard parser can parse it
```

------

### Test 11 — XML → Dashboard

Проверить полный pipeline:

```text
Simulation
 ↓
XML
 ↓
Parser
 ↓
Dashboard model
 ↓
Statistics
```

Dashboard должен получить те же ключевые значения, которые были в simulation state.

------

### Test 12 — API

Проверить:

```text
start
stop
pause
reset
state
config
metrics
scenario
health
```

и корректные HTTP status codes.

------

### Test 13 — Service Failure

Остановить Smart Intersection.

Проверить:

```text
Dashboard remains available
```

и показывает:

```text
Smart Intersection unavailable
```

------

### Test 14 — Simulation Restart

```text
START
 ↓
STOP
 ↓
RESET
 ↓
START
```

Проверить отсутствие:

- дублирования объектов;
- утечек;
- старых автомобилей;
- старых метрик;
- неправильного состояния светофоров.

------

### Test 15 — Long Run

Запустить simulation минимум на несколько виртуальных часов.

Например:

```text
simulation speed = 10x
simulation duration = 2 hours
```

Проверить:

- отсутствие деградации;
- отсутствие бесконтрольного роста памяти;
- отсутствие накопления старых объектов;
- корректность статистики.

# 71. Запрет на фиктивную реализацию

Особенно важно.

Нельзя создавать видимость работы через:

- заранее записанные анимации;
- статичные автомобили;
- случайное перемещение объектов без правил;
- фиктивные значения статистики;
- захардкоженные XML;
- захардкоженные данные Dashboard;
- имитацию API без реального соединения.

Если на экране отображается:

```text
17 cars
```

это число должно соответствовать реальному состоянию Simulation Engine.

Если отображается:

```text
TL-01 GREEN
```

реальный объект светофора в Simulation Engine должен находиться в состоянии GREEN.

Если XML содержит:

```xml
<vehicleCount>17</vehicleCount>
```

в симуляции действительно должно находиться соответствующее количество учитываемых транспортных объектов.

# 72. Главное архитектурное требование

Должна существовать единая цепочка:

```text
                    SMART INTERSECTION
                           │
                    Simulation Engine
                           │
          ┌────────────────┼────────────────┐
          │                │                │
       Renderer       Traffic Analysis   Metrics
          │                │                │
          │          Traffic Controller    │
          │                │                │
          └────────────────┼────────────────┘
                           │
                          XML
                           │
                           ▼
                      Main Project
                           │
                       XML Parser
                           │
                           ▼
                       Dashboard
```

3D-визуализация, XML и Dashboard должны использовать **одно и то же состояние симуляции**, а не три независимые реализации.

# 75. Итоговая цель Smart Intersection

Итоговый Smart Intersection должен восприниматься как самостоятельный виртуальный цифровой двойник перекрёстка.

Пользователь должен видеть:

```text
┌──────────────────────────────────────────────┐
│              SMART INTERSECTION              │
│                                              │
│       🚗 → → →                               │
│                  🚦                         │
│       ────────────────                       │
│             🚶 🚶                             │
│       ═══════════════                        │
│                         ← ← 🚗               │
│                                              │
│  Traffic: 32 vehicles                        │
│  Pedestrians: 14                             │
│  Queue: 7                                     │
│  Avg waiting: 12.4 sec                       │
│  Mode: AUTO                                  │
└──────────────────────────────────────────────┘
```

При этом за визуальной частью должна находиться реальная симуляция, а не статическая анимация.

Smart Intersection должен быть самостоятельным сервисом, который можно:

1. запустить отдельно;
2. протестировать отдельно;
3. подключить к основному проекту через API;
4. использовать без физического Raspberry Pi;
5. использовать без камеры;
6. использовать без YOLO;
7. передавать результаты через XML;
8. подключить к существующему Dashboard;
9. заменить Renderer без переписывания simulation engine;
10. в будущем подключить к реальному Traffic Controller и физическому перекрёстку.
